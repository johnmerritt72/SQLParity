# What's New in SQLParity 1.4.2

This release fixes two correctness bugs in the 1.4.1 permission-comparison feature and adds server-message visibility to **Apply Live**.

## 🐛 Fixed

### Apply Live now actually applies permissions
In 1.4.1, **Apply Live silently skipped every GRANT / REVOKE / DENY**. The DDL pass ran each object's `CREATE OR ALTER`, but the permission-script generator was never invoked, so:

- Apply Live reported *"all N changes applied successfully"*.
- `sys.database_permissions` on the destination was unchanged.
- Refreshing the comparison kept showing the same permission diff.

Apply Live now runs a dedicated **Permissions pass** after the DDL pass — mirroring the script-file generator — inside the same transaction. If a permission step fails, the whole apply rolls back, including the DDL.

### A missing principal no longer aborts the script
The per-grantee existence guard used to be:

```sql
IF NOT EXISTS (SELECT 1 FROM sys.database_principals WHERE name = N'PTMUser')
    THROW 50000, 'Principal [PTMUser] does not exist on destination…', 1;
```

So the **first** missing principal stopped the entire batch, and any subsequent grantees' grants were skipped. The guard now wraps each grantee's block:

```sql
IF EXISTS (SELECT 1 FROM sys.database_principals WHERE name = N'PTMUser')
BEGIN
    GRANT EXECUTE ON OBJECT::[dbo].[Foo] TO [PTMUser];
END
ELSE
    PRINT 'Skipped permissions for [PTMUser]: principal does not exist on destination.';
```

A missing principal is **skipped** (with a breadcrumb in SSMS's **Messages** tab) and the rest of the script — including grants for principals that *do* exist — still runs.

## ✨ Added

### Apply Live surfaces server messages
Server-side `PRINT` and low-severity `RAISERROR` messages emitted during each step are now captured per step. The Apply Live result dialog gains a **Server messages** section, e.g.:

```
All 3 changes applied successfully.

Server messages:
  • [dbo].[ThreeGranteeProc] (permissions): Skipped permissions for [MissingUser]: principal does not exist on destination.
```

The same messages are written to the apply-history file under each step's `Info:` lines. So a silently-skipped grantee can no longer go unnoticed.
